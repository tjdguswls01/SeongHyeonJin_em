Slide 4: Kernel 3를 한 문장으로 정의

슬라이드 내용: 정의, 핵심 입력, 핵심 출력

발표 대본:
"먼저 커널의 정의부터 명확히 하겠습니다. Visa "Kernel 3를 한 문장으로 정의하면, Visa의 비접촉 핵심 규격인 qVSDC 프로토콜을 0.5초 이내의 초고속으로 처리하기 위해 설계된 전용 L2 엔진입니다. 단순히 APDU를 전달하는 것이 아니라, qVSDC의 핵심인 고속 데이터 수집과 암호화 검증(fDDA)을 수행하는 것이 존재 이유입니다." 단순히 하위 계층과 스마트카드 사이에서 APDU 패킷만 무지성으로 전송하는 모듈이 아닙니다. 단말 거래 조건과 선택된 애플리케이션 정보를 입력받아 내부 상태(TVR, TSI 등)를 갱신하고, 결과적으로 Approved, Declined, Online Request, Try Another Interface 같은 구체적인 'Outcome'을 생성하여 상위 결제 애플리케이션에 전달하는 지능형 비즈니스 레이어입니다."

Slide 5: Kernel 구조를 보는 다섯 관점

슬라이드 내용: 구조 관점 5가지, 주의점

발표 대본:
"소스를 분석하기 전 사양서를 볼 때 우리는 다섯 가지 관점을 관통해야 합니다. 시스템 계층 구조, 커널과 주변 모듈 간의 책임 경계, 거래의 처리 상태 전이도, 메모리에 적재되는 데이터 구조, 그리고 상하위 입출력 인터페이스가 그것입니다. 이 다섯 관점을 정립해야만 사양서의 추상적인 다이어그램과 소스 코드의 복잡한 함수 호출 체인을 동등한 기준으로 비교할 수 있습니다. 특히 주의할 점은 소스 상에 특정 사양을 지원하는 함수가 '단순히 존재한다는 사실'과, 그것이 실제 결제 거래의 활성 경로(Active Path)에 '정상적으로 연결되어 실행된다는 사실'은 완전히 별개라는 것입니다. 이 점에 주의하며 구조를 살펴보겠습니다."

Slide 6: EMV L1 · L2 · L3

슬라이드 내용: 계층별 기능, 경계의 중요성

발표 대본:
"시스템 아키텍처 관점에서 본 L1, L2, L3 계층입니다. L1은 물리적인 RF 무선 전송 드라이버와 ISO 14443 송수신 규격을 담당합니다. L3는 POS 시스템의 비즈니스 도메인 영역으로 금액과 거래 유형을 준비하고 UI 처리 및 호스트 통신을 관장합니다. 우리가 분석할 L2 Visa Kernel 3는 그 중간에 위치하여 가교 역할을 합니다. 카드로부터 넘어온 APDU 바이트 데이터의 문맥적 의미를 이해하고 결제 상태를 제어합니다. 이 경계가 뚜렷해야 필드에서 오작동이 일어났을 때 이것이 단순 RF 노이즈(L1) 문제인지, 커널 규칙 불일치(L2) 문제인지, 혹은 승인 호스트 서버 오작동(L3) 문제인지를 정확히 격리하여 대응할 수 있습니다."

Slide 7: 결제 시스템에서 Kernel 3의 위치

슬라이드 내용: 아키텍처 이미지 슬라이드 (Host -> Kernel -> APDU Transport -> RF -> Card)

발표 대본:
"제공된 개념도를 보시면 계층 구조가 직관적으로 도식화되어 있습니다. 상위 호스트 결제 소프트웨어에서 트랜잭션이 기동되면 커널 3로 비즈니스 요구사항이 주입되고, 커널은 이에 맞는 APDU 패킷을 조립하여 하위 APDU Transport 인프라와 RF 트랜시버 칩셋으로 흘려보냅니다. 이 그림이 시사하는 바는 명확합니다. Kernel은 결제 트랜잭션의 중추(Brain) 역할을 수행하며, 실제 물리적인 미디어 연결은 완전히 추상화하여 하위 드라이버에 위임하는 구조를 띄고 있다는 점입니다."

Slide 8: Kernel 3의 책임

슬라이드 내용: 핵심 책임 (카드 통신 중, 카드 통신 후)

발표 대본:
"커널 3의 실제 책임 범위를 카드와의 물리적 접촉 타이밍을 기준으로 쪼개어 보겠습니다. 먼저 카드가 RF 안테나 필드 위에 올라와 통신을 나누는 '카드 통신 중' 단계입니다. 커널은 거래를 초기화하고 단말의 속성 데이터를 바인딩한 후, GPO 명령과 READ RECORD 명령을 연속적으로 발행하여 필요한 카드 원격 데이터를 신속하게 확보합니다. 데이터 수집이 끝나 카드가 안테나를 벗어난 '카드 통신 후' 단계에서는, 확보한 카드 데이터를 기반으로 한도 제한성 검사, 오프라인 데이터 인증(fDDA), CVM(Cardholder Verification Method) 판단 등의 복잡한 로컬 비즈니스 처리를 수행한 후 온라인 처리 여부와 최종 Outcome 방향을 빌드업합니다."

"여기서 중요한 점은 Kernel 3가 왜 일반 EMV와 다른가 하는 점입니다. 바로 qVSDC 규격 때문입니다. qVSDC는 카드를 탭하는 짧은 순간에 모든 결제 정보를 '한 번의 GPO'로 긁어오는 기술입니다. Kernel 3는 이 qVSDC 로직을 탑재하여, 사용자가 카드를 떼고 난 뒤에도 배경에서 fDDA라는 고속 서명 검증을 완료할 수 있게 해줍니다. 즉, qVSDC는 Kernel 3가 수행하는 비즈니스 로직의 '영혼'과 같습니다."

Slide 9: Kernel 3가 직접 하지 않는 일

슬라이드 내용: Kernel 밖의 책임 (하위 계층, 상위 계층)

발표 대본:
"프로젝트 범위 설정 및 디버깅 시 가장 많이 오해하는 부분입니다. 'Kernel 3가 직접 수행하지 않는 영역'을 명확히 격리해야 합니다. 하위 RF 칩셋의 아날로그 신호 세기 제어, 폴링 루틴을 통한 카드 탐색 및 활성화 처리는 L1 인터페이스 드라이버의 전적인 영역입니다. 또한 화면에 안내 문구를 띄우고, 승인 부저를 울리고, 영수증을 인쇄하거나 백엔드 승인 서버와 TCP/IP 통신을 나누는 것은 모두 L3 결제 애플리케이션의 몫입니다. 커널은 표준 규격에 명시된 형태의 요청(Outcome 파라미터)을 상위 애플리케이션에 전달할 뿐, 화면을 직접 렌더링하거나 통신 소켓을 열지 않습니다."

Slide 10: Kernel의 입력

슬라이드 내용: 거래 입력, 카드 입력, 오류 영향

발표 대본:
"커널이 거래를 판정하기 위해 받아들이는 원천 소스입니다. 단말기 측에서는 금액, 통화 코드, 거래 일자, 단말 제한 금액, 단말 기능 조건 등의 정보가 공급됩니다. 카드 측에서는 SELECT 및 GPO의 결과 레코드를 통해 AIP, AFL, 그리고 트랙 2 데이터 등의 응답이 입력됩니다. 이 입력값들은 단순 기록용이 아니라 GPO 명령에 탑재할 PDOL 데이터 셋을 파싱하고 생성하는 데 실시간으로 사용됩니다. 만약 상위 시스템에서 넘겨준 통화 코드나 거래 금액 포맷이 잘못되어 커널 내부 버퍼에 주입되면, 비록 APDU 통신 자체는 정상 수신되었을지라도 최종 단계에서 카드에 의해 거래 경로가 아예 거절되는 부작용을 낳게 됩니다."

Slide 11: Kernel의 내부 상태

슬라이드 내용: 내부 데이터, 필요성, 관리 원칙

발표 대본:
"결제가 진행되는 동안 커널 내부에는 고유의 상태 저장 메모리 공간이 운영됩니다. AIP, AFL 같은 제어 데이터부터 카드 암호문 결과값인 Application Cryptogram(AC), 발급사 애플리케이션 데이터(IAD) 등이 실시간으로 캐싱됩니다. 특히 TVR(Terminal Verification Results)과 TSI(Transaction Status Information) 같은 표준 비트 마스크 데이터는 거래 단계마다 축적된 상태 판정 결과가 업데이트됩니다. 이 상태 관리가 왜 중요할까요? 전 단계의 비즈니스 조건이 후속 단계의 로컬 판정과 온라인 호스트 가부 판정에 누적되어 연쇄 반응을 일으키기 때문입니다. 따라서 거래가 기동되는 즉시 이 영역은 무조건 완전한 제로 셋으로 초기화되어야 하며, 예외 상황이 발생하더라도 일관성을 유지해야 합니다."

Slide 12: Kernel의 출력: Outcome

슬라이드 내용: 주요 결과(Outcome), 구현 관점

발표 대본:
"커널 3 프로세싱의 최종 결과물은 Outcome 구조체입니다. 승인 완료인 Approved, 거절인 Declined, 호스트 망 승인이 필요한 Online Request, 카드 접촉 인터페이스 등 타 매체 전환을 유도하는 Try Another Interface 등이 핵심 값입니다. 여기서 개발 및 검증 엔지니어로서 주목해야 할 구현 관점이 있습니다. 당사 단말 소스 코드 내부에서 반환하는 데이터 포맷이 단순히 '임의의 자체 에러 코드'와 '일반 raw TLV 버퍼'의 나열에 그친다면, 해외 EMV 결제 인증 시 요구하는 표준 Outcome 명세와 완벽하게 대칭되는지를 별도로 전수 검사하여 누락 포인트를 보정해야 합니다."

Slide 13: 지원 범위와 선택 기능

슬라이드 내용: 기본 흐름, 조건부 및 선택 기능, 분석 원칙

발표 대본:
"사양서의 범위 획정 부분입니다. 기본 흐름은 Combination Selection 단계에서 적합한 결제 AID 조합을 확보한 뒤, GPO 및 READ RECORD 단계로 카드 정보를 독출하고, 오프라인 데이터 인증(fDDA), CVM, 온라인 완성 단계로 이어집니다. 다만, 여기서 오프라인 결제를 전면 지원하는 단말이라면 고속 오프라인 서명 검증 기법인 fDDA 처리가 '필수 사양'이 됩니다. 반면, 카드의 승인 통계를 세부 관리하는 IDS(Integrated Data Storage) 사양이나 카드 재제시를 통해 발급사 상태 코드를 강제 주입하는 Issuer Update 기능은 아키텍처 관점에서 '선택적 구현(Optional)' 스펙입니다. 프로젝트의 요구 단가를 맞추기 위해 어디까지 구현 범위를 설정해야 하는지 이 기준표를 보고 정확히 저울질해야 합니다."

"지원 범위를 보시면 Kernel 3는 MSI 모드도 수용하지만, 본질적인 타겟은 qVSDC 모드입니다. TTQ 비트 설정을 통해 카드가 qVSDC 능력이 있는지 확인하고, 가능하다면 가장 보안 수준이 높은 qVSDC 경로로 결제를 유도하는 것이 Kernel 3의 핵심 임무입니다."

Slide 14: Figure 2-1 · 전체 거래 흐름

슬라이드 내용: 규격서 다이어그램 (Entry Point -> GPO -> READ RECORD -> Card Read Complete -> 판단 -> Outcome)

발표 대본:
