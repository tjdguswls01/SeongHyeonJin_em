PCI PTS POI는 무엇을 검증하는가

POI 장치

Point of Interaction에서 카드와 사용자의 결제 입력을 받는 장치가 민감 기능을 안전하게 수행하는지 검증한다.

제품 보안 평가

기능 적합성보다 물리 침입, 소프트웨어 변조, 키·PIN 노출, 인터페이스 악용에 견디는지를 평가한다.

구분: PCI DSS가 운영 환경을 다룬다면 PCI PTS POI는 장치 자체의 보안 특성을 중심으로 평가한다.

03

누가 무엇을 증명하는가

Vendor

장치 설계, 펌웨어, 키·PIN 처리, 제조·배포 절차와 평가 샘플을 제공한다.

PCI-recognized Laboratory

보안 요구사항과 Derived Test Requirements에 따라 문서 검토와 공격 시험을 수행한다.

PCI SSC

평가 결과를 검토하고 승인 제품을 Approved PTS Device 목록과 보안 평가 정보로 공개한다.

결과: 승인은 특정 모델, 하드웨어·펌웨어 버전, 기능과 조건에 묶인다.

04

장치 유형과 적용 기능을 먼저 정한다

PIN 입력 장치

PIN Entry Device와 Encrypting PIN Pad처럼 PIN 입력과 암호화를 수행하는 기능이 핵심 범위이다.

무인·통합 장치

Unattended Payment Terminal과 Integrated POS는 설치 환경과 구성에 따라 물리·운영 위험이 달라진다.

선택 기능

SRED, Open Protocol, Contactless, Secure Card Reader 등 신청 기능에 따라 추가 요구사항이 적용된다.

출발점: 모든 장치에 모든 요구사항을 적용하지 않고 제품 기능과 평가 모듈을 먼저 확정한다.

05

무엇을 보호해야 하는가

PIN과 Cryptographic Keys

입력 순간부터 암호화·전송·삭제까지 평문 PIN과 비밀키가 노출되지 않아야 한다.

Sensitive Functions

펌웨어, 보안 설정, 키 주입, 관리자 명령과 정상 동작 상태의 무결성을 보호한다.

Account Data

PAN과 Track Data는 SRED를 신청한 장치에서 암호화 범위와 복호화 통제를 포함해 추가 보호한다.

정확한 범위: PAN 전체 보호는 모든 PTS 장치의 동일한 기본 요구가 아니라 신청 기능에 따라 달라진다.

06

Security Requirements와 DTR의 관계

Security Requirements

장치가 달성해야 할 보안 목표를 정의하며 적용성은 장치 유형과 신청 기능에 따라 결정된다.

Derived Test Requirements

DTR은 각 요구사항을 평가할 증빙, 시험 조건, 공격 방법과 판정 기준으로 구체화한다.

실무 의미: 요구사항과 연결된 DTR, Technical FAQ를 함께 보아야 시험 기대치를 이해할 수 있다.

08

Tamper 보호는 세 가지 방식으로 구성된다

Tamper Evidence

봉인과 외관 변화처럼 침입 시도가 운영자에게 명확한 흔적으로 남는다.

Tamper Resistance

케이스, 차폐, Mesh와 부품 배치가 민감부 접근에 필요한 시간과 기술을 높인다.

Tamper Detection and Response

Switch, Mesh와 센서가 침입을 감지하면 키 삭제나 기능 비활성화 같은 반응을 실행한다.

설계 기준: 흔적, 저항, 자동 탐지·반응을 제품 위험과 기능에 맞게 조합한다.

09

Attack Potential은 공격 난이도를 점수화한다

공격 자원

공격에 필요한 경과 시간, 전문 지식, 장비, 샘플 수와 접근 기회를 평가한다.

공격 시나리오

식별, 준비, 실행 단계의 비용을 합산해 실현 가능한 공격인지 판단한다.

판정

요구되는 최소 Attack Potential보다 낮은 비용으로 자산을 침해할 수 있으면 보호가 부족하다.

핵심: 절대적으로 뚫리지 않는 장치가 아니라 규정된 공격 능력에 견디는 장치를 증명한다.

10

Side-Channel과 환경 조작도 물리 공격이다

정보 누출

전력, 전자기파, 타이밍과 오류 반응에서 PIN 또는 키 연산의 단서를 얻으려 한다.

Fault Injection

전압, Clock, 온도, Laser 같은 비정상 조건으로 보안 검사를 건너뛰거나 비밀을 노출시킨다.

Monitoring

전압·Clock·온도와 보안 센서 상태를 감시하고 허용 범위를 벗어나면 안전 상태로 전환한다.

대응: 회로 보호뿐 아니라 측정 결과와 센서 임계값의 근거를 평가 자료로 제시한다.

11

Software Management가 신뢰 실행을 만든다

Authenticity

실행 파일과 Firmware가 승인된 주체가 서명한 정식 배포물인지 확인한다.

Integrity

부팅과 실행 중 코드, 설정, 보안 데이터가 변조되지 않았는지 검증한다.

Version Control

버전 식별, Rollback 통제, 변경 이력과 승인된 Software 목록을 유지한다.

목표: 승인되지 않은 Software가 설치되거나 실행되는 경로를 제거한다.

12

Secure Boot와 Update는 하나의 신뢰 사슬이다

Boot Chain

변경하기 어려운 Root of Trust에서 Bootloader, OS, Application 순서로 서명과 무결성을 검증한다.

Secure Update

Update Package의 출처·무결성·버전·대상 장치를 확인하고 실패 시 안전하게 복구하거나 실행을 차단한다.

포함 범위: 개발·진단 Interface와 비상 복구 경로도 동일한 인증과 권한 통제를 적용한다.

13

Key Management는 생성부터 파기까지 이어진다

Key Lifecycle

생성, 주입, 저장, 사용, 교체, 백업과 파기 단계마다 비밀성과 무결성을 유지한다.

Separation

서로 다른 목적의 Key를 분리하고 Dual Control, Split Knowledge와 역할 기반 권한을 적용한다.

Cryptographic Control

승인된 Algorithm과 Key Length를 사용하고 Key Check Value, TR-31 Key Block 같은 보호 형식을 적용한다.

실패 영향: Key가 노출되면 PIN 암호화와 장치 인증 등 여러 보호 계층이 동시에 무너진다.

Logical Security
14

PIN Management는 입력 순간을 보호한다

Secure Entry

키 배열, Touch 입력, Display Prompt와 PIN Buffer가 관찰·주입·재사용 공격에 노출되지 않아야 한다.

Immediate Protection

입력된 PIN은 승인된 PIN Block 형식으로 즉시 암호화하고 평문 복사본과 잔여 데이터를 제거한다.

Bypass Prevention

Non-PIN Prompt, Cancel, Timeout, 오류 경로가 PIN 보호 기능을 우회하거나 값을 노출하지 않아야 한다.

원칙: 평문 PIN은 필요한 최소 영역과 최소 시간에만 존재한다.

15

SRED는 계정 데이터를 읽는 순간부터 암호화한다

Secure Reading

Magnetic Stripe, Contact, Contactless Interface에서 읽은 Account Data를 정의된 보호 지점에서 즉시 암호화한다.

Data Control

평문 PAN·Track Data의 저장, 표시, 로그, 진단 출력과 비인가 복호화를 제한한다.

Key Separation

SRED Data Encryption Key를 다른 목적의 Key와 분리하고 암호문과 관련 Metadata의 무결성을 보호한다.

적용성: SRED는 선택 평가 모듈이며 신청하지 않은 장치에 동일 범위가 자동 적용되는 것은 아니다.

취약점은 출시 후에도 관리한다

Vulnerability Mitigation

공개 취약점, 사용 Library와 공격 동향을 추적하고 영향 분석, Patch, 고객 통지와 배포 절차를 운영한다.

Policies and Procedures

Secure Development, Code Review, Access Control, Incident Response와 Change Control을 문서화하고 실제 기록을 남긴다.

평가 관점: 보안 기능의 존재뿐 아니라 반복 가능한 관리 절차와 책임 주체를 확인한다.

17

Open Protocol은 외부 연결을 신뢰 경계로 본다

Mutual Authentication

Network와 외부 장치가 민감 명령을 보내기 전에 통신 상대와 장치의 신원을 확인한다.

Confidentiality and Integrity

Least Privilege

서비스, Port, Remote Management와 Debug 기능을 최소화하고 기능별 권한과 Audit Log를 적용한다.

범위: USB, Ethernet, Wi-Fi, Cellular 등 외부에서 접근 가능한 Protocol과 관리 기능을 분석한다.

제조 단계에서 장치 신뢰가 시작된다

Controlled Manufacturing

승인된 부품, Firmware와 생산 Tool을 사용하고 작업자·공정·샘플의 추적성을 유지한다.

Secure Personalisation

Inventory and Reconciliation

생산 수량, 불량품, 폐기품, 보안 부품과 Key Material의 이동을 대조해 유실과 대체를 탐지한다.

목표: 평가된 설계와 실제 출하 제품이 동일하다는 Chain of Custody를 만든다.

19

제조사에서 KIF와 고객까지 신뢰를 이어 간다

Secure Shipment

포장, 봉인, Serial Number, 운송 기록과 수령 확인으로 이동 중 교체·개봉을 탐지한다.

Key Injection Facility

KIF는 Key 주입 대상 장치와 작업 권한을 확인하고 Key가 평문으로 노출되지 않도록 통제한다.

Deployment and Repair

설치 전 식별·외관을 확인하고 수리·반품 장치의 Key와 민감 데이터를 제거한 뒤 재평가 조건을 판단한다.

핵심: 평가실을 나온 뒤에도 장치 식별과 보안 상태가 추적되어야 한다.

20

공격을 감지하면 안전한 상태로 전환한다

Zeroisation

민감 Key와 평문 PIN·Account Data를 복구하기 어렵게 제거한다.

Inoperative State

보안 기능을 우회한 상태로 결제를 계속하지 못하도록 민감 동작과 Interface를 차단한다.

Controlled Recovery

복구와 재활성화는 인증된 절차, 권한, Firmware와 Key 재주입을 통해서만 가능하게 한다.

Fail Secure: 오류나 전원 이상에서도 보호 수준이 낮아지는 방향으로 실패하면 안 된다.

승인 후 변경도 보안 영향으로 판단한다

Change Identification

24

개발 단계에서 보안 요구를 설계 항목으로 바꾼다

Asset and Boundary

PIN, Key, Account Data, Firmware가 어디에서 생성·이동·저장·삭제되는지와 신뢰 경계를 표시한다.

Threat and Control

침입, Side-Channel, Debug, Update, Network, 공급망 위협마다 예방·탐지·반응 통제를 배치한다.

Evidence by Design

Requirement ID를 설계, Source, Test Case와 문서에 연결해 평가 직전에 증빙을 다시 만들지 않게 한다.

효율: 보안을 마지막 시험 단계가 아니라 Architecture와 개발 산출물의 구조로 관리한다.

25

TIT-ICRFReader는 제품 역할부터 확인해야 한다

현재 확인되는 역할

STM32F103xG, PN5180, USB CCID·RS232와 EMV·NFC 처리 기능을 가진 Contactless Reader Firmware이다.

PTS POI 여부

독립적으로 PIN 입력, Key 관리, SRED 같은 POI 기능을 수행하지 않는 Reader Component라면 전체 PCI PTS POI 대상과 동일하지 않을 수 있다.

확인할 질문

최종 판매 제품의 경계, PIN·Account Data 처리, Key 보유, 관리 Interface와 신청 모듈을 정한 뒤 적용 요구사항을 확정한다.

주의: MCU와 NFC Reader가 존재한다는 사실만으로 PCI PTS 인증 대상 또는 충족 여부를 단정할 수 없다.
